# 01 — A2A / ACP / MCP: protocol scope, message identity, and the peer-session-write question

**Status:** Research brief for `dsh-openai-live` (realtime-voice plugin: SILENT NOTE = model-facing context that does not start a turn; VISIBLE SAY = starts a turn, attributed to the voice, shown in the transcript).
**Method:** Specs fetched directly (web_extract / raw spec text). Every claim below carries a primary-source URL. Items I could not confirm against a primary source are marked **UNVERIFIED**.
**Spec versions read:** A2A `1.0.0` (latest released), ACP docs (protocol v1 stable, v2 in migration), MCP (docs as published, protocol revisions dated `2025-06-18`).

---

## 0. TL;DR — the three-axis distinction

| Protocol | Axis | Counterpart | Who is on the other end | Primary source |
| --- | --- | --- | --- | --- |
| **A2A** (Agent2Agent) | agent ↔ **agent** | a peer agent | another autonomous agent, "often opaque" | https://a2a-protocol.org/latest/topics/a2a-and-mcp/ |
| **ACP** (Agent Client Protocol) | agent ↔ **client/editor** | an IDE / client UI | the human-facing editor that hosts the agent | https://agentclientprotocol.com/get-started/introduction |
| **MCP** (Model Context Protocol) | agent ↔ **tool / context-server** | tools, resources, prompts | a capability/data provider, not a peer | https://modelcontextprotocol.io/docs/learn/architecture |

Source for the split, verbatim (A2A and MCP guide):
> "MCP is vertical. It deepens a single agent. ... A2A is horizontal. It connects agents across that boundary. ... A2A connects the agents to each other; MCP connects each agent to its own tools."
> — https://a2a-protocol.org/latest/topics/a2a-and-mcp/

**Ruling for a PEER SESSION WRITE** (one agent session writing a message into a *sibling agent session*): **A2A is the correct axis.** It is the only one of the three defined as agent↔agent with a *peer* Message carrying `role` + `contextId` + `taskId` + `metadata` + `referenceTaskIds`. ACP is the editor axis (wrong counterpart); MCP is the tool axis (wrong counterpart). Caveat: A2A has **no native "silent note that does not start a turn"** — every A2A `Message` is modeled as initiating or continuing a `Task`. See §4.4.

## 1. A2A (Agent2Agent) Protocol — v1.0.0

Primary spec: https://a2a-protocol.org/latest/specification/ · canonical proto: https://a2a-protocol.org/latest/definitions/ · companion repo: https://github.com/a2aproject/a2a/blob/main/docs/specification.md

### 1.1 Core message/task model

A2A organizes into three layers — data model, operations, bindings — and the *single authoritative normative definition* is the proto file:

> "the file `spec/a2a.proto` is the single authoritative normative definition of all protocol data objects and request/response messages."
> — https://a2a-protocol.org/latest/specification/ (§1.4 Normative Content)

Core concepts, verbatim (https://a2a-protocol.org/latest/specification/ §2.2):
- **Agent Card:** "A JSON metadata document published by an A2A Server, describing its identity, capabilities, skills, service endpoint, and authentication requirements."
- **Message:** "A communication turn between a client and a remote agent, having a `role` ("user" or "agent") and containing one or more `Parts`."
- **Task:** "The fundamental unit of work managed by A2A, identified by a unique ID. Tasks are stateful and progress through a defined lifecycle."
- **Part:** "The smallest unit of content within a Message or Artifact. Parts can contain text, file references, or structured data."
- **Artifact:** "An output (e.g., a document, image, structured data) generated by the agent as a result of a task, composed of `Parts`."
- **Context:** "An optional identifier to logically group related tasks and messages."
- **Extension:** "A mechanism for agents to provide additional functionality or data beyond the core A2A specification."

**Message → Part** relation is explicit: Messages SHOULD carry communication; deliverables go in Artifacts:
> "Messages SHOULD NOT be used to deliver task outputs. Results SHOULD BE returned using Artifacts associated with a Task. This separation allows for a clear distinction between communication (Messages) and data output (Artifacts)."
> — https://a2a-protocol.org/latest/specification/ (§3.7)

**Agent Card** fields, verbatim (https://a2a-protocol.org/latest/specification/ §4.4.1):
```
name, description, supportedInterfaces, provider, version, documentationUrl,
capabilities, securitySchemes, securityRequirements, defaultInputModes,
defaultOutputModes, skills, signatures, iconUrl
```
- Discovery well-known URI: `https://{server_domain}/.well-known/agent-card.json` (§8.2; note v1.0 uses `agent-card.json`).
- `capabilities` = `{ streaming, pushNotifications, extensions, extendedAgentCard }` (§4.4.3).
- Agent Cards MAY be signed with JWS / RFC 7515, canonicalized per RFC 8785 (§8.4) — *this is the only "provenance" primitive A2A defines, and it is on the card, not on messages.*

**Task** fields, verbatim (https://a2a-protocol.org/latest/definitions/):
```
message Task {
  string id = 1 [REQUIRED];          // server-generated
  string context_id = 2;
  TaskStatus status = 3 [REQUIRED];
  repeated Artifact artifacts = 4;
  repeated Message history = 5;
  google.protobuf.Struct metadata = 6;
}
```

**Message** fields, verbatim (https://a2a-protocol.org/latest/definitions/):
```
message Message {
  string message_id = 1 [REQUIRED];   // created by the message creator
  string context_id = 2;
  string task_id = 3;
  Role role = 4 [REQUIRED];           // "Identifies the sender of the message."
  repeated Part parts = 5 [REQUIRED];
  google.protobuf.Struct metadata = 6;
  repeated string extensions = 7;
  repeated string reference_task_ids = 8;
}
```

**Part** is a `oneof` (exactly one of), verbatim:
```
message Part {
  oneof content {
    string text = 1;
    bytes raw = 2;    // base64 in JSON
    string url = 3;
    google.protobuf.Value data = 4;
  }
  google.protobuf.Struct metadata = 5;
  string filename = 6;
  string media_type = 7;
}
```
> "Note: A `Part` MUST contain exactly one of the following: `text`, `raw`, `url`, `data`"
> — https://a2a-protocol.org/latest/specification/ (§4.1.6)

**Artifact**, verbatim (https://a2a-protocol.org/latest/specification/ §4.1.7):
```
artifactId (required, unique within a task), name, description,
parts (required, ≥1 Part), metadata, extensions
```

### 1.2 Sender identity & provenance on a message

**The single most decision-relevant finding for this plugin:** in A2A v1.0 a `Message` has **no `senderId` / `recipientId` / agent-identity field**. The only sender attribute on a Message is `role`:

> **Role** — "Defines the sender of a message in A2A protocol communication."
> | Value | Description |
> | `ROLE_UNSPECIFIED` | The role is unspecified. |
> | `ROLE_USER` | The message is from the client to the server. |
> | `ROLE_AGENT` | The message is from the server to the client. |
> — https://a2a-protocol.org/latest/specification/ (§4.1.5)

So a Message distinguishes exactly two actors — *client side* (`ROLE_USER`) vs *server side* (`ROLE_AGENT`) — not the concrete identity of a specific agent/session. The field describing `role` is literally the only one the spec annotates as "Identifies the sender of the message."

Concrete agent identity is deliberately pushed *out of A2A semantics*:
> "A2A treats agents as standard enterprise applications, relying on established web security practices. **Identity information is handled at the protocol layer, not within A2A semantics.**"
> — https://a2a-protocol.org/latest/specification/ (§7 Authentication and Authorization)

The provenance/id-threading fields that *do* exist on a Message:
- `contextId` — "logically groups multiple related `Task` and `Message` objects ... the same conversational session" (§3.4.1).
- `taskId` — "a unique identifier for a `Task` object, representing a stateful unit of work" (§3.4.2).
- `referenceTaskIds` — "A list of task IDs that this message references for additional context." (definitions; §3.4.3: "Clients SHOULD use the `referenceTaskIds` field in `Message` to explicitly reference related tasks").
- `metadata` — free-form `Struct`; the extension hook for anything the core model lacks.
- `extensions` — URIs of extensions contributing to the message.

**`senderId` is NOT an A2A field.** It appears only in third-party/derived material, not the official spec — treat any `senderId`-bearing A2A schema as a vendor extension:
- a2a-node-sdk (community SDK) defines its own `Message { id, conversationId, senderId, recipientId, parts, timestamp, metadata }` — **not the official spec**: https://dexwox-innovations-org.github.io/a2a-node-sdk/docs/protocol/
- Cloud Security Alliance proposal on Agentic AI IAM *invents* `senderId`/`recipientId`/`protocolVersion` in an "a2aHeader" and calls it "Fields defined by A2A spec" — this is **incorrect**; those are not A2A fields: https://cloudsecurityalliance.org/artifacts/agentic-ai-identity-and-access-management-a-new-approach

> **Decision implication:** if the plugin needs a verified sender identity per message, A2A gives you only `role` + transport-layer auth + optional JWS on the Agent Card. A per-message sender identity must ride in `metadata` or a declared A2A extension.

### 1.3 Streaming (SSE) model and multi-turn / input-required state

**Streaming** (source: https://a2a-protocol.org/latest/topics/streaming-and-async/):
- Server must advertise `capabilities.streaming: true` in the Agent Card.
- Client calls `SendStreamingMessage` (v1.0 rename of `message/stream` — https://a2a-protocol.org/latest/whats-new-v1/).
- Transport is **Server-Sent Events**: server responds `HTTP 200 OK` + `Content-Type: text/event-stream`, connection stays open.
- Each SSE `data` field carries a JSON-RPC 2.0 Response whose `result` is a `StreamResponse` with exactly one payload:
```
message StreamResponse {
  oneof payload {
    Task task = 1;
    Message message = 2;
    TaskStatusUpdateEvent status_update = 3;
    TaskArtifactUpdateEvent artifact_update = 4;
  }
}
```
  (https://a2a-protocol.org/latest/definitions/)
- Stream shapes (§3.1.2): **Message-only stream** (returns a `Message`, exactly one, then closes) or **Task lifecycle stream** (begins with a `Task`, then zero or more `TaskStatusUpdateEvent`/`TaskArtifactUpdateEvent`, closes on terminal state).
- Ordering is guaranteed: "All implementations MUST deliver events in the order they were generated. Events MUST NOT be reordered during transmission." (§3.5.2)
- Reconnect via `SubscribeToTask` if the SSE connection drops (§3.1.6); multi-stream per task supported.
- v1.0 breaking changes: stream events dropped the `kind` discriminator and the `final` boolean — event type is now determined by the JSON member name (`statusUpdate` / `artifactUpdate`), and closure signals completion (https://a2a-protocol.org/latest/whats-new-v1/).

**Task states** (verbatim `TaskState` enum, https://a2a-protocol.org/latest/definitions/):
```
TASK_STATE_UNSPECIFIED, TASK_STATE_SUBMITTED, TASK_STATE_WORKING,
TASK_STATE_COMPLETED, TASK_STATE_FAILED, TASK_STATE_CANCELED,
TASK_STATE_INPUT_REQUIRED, TASK_STATE_REJECTED, TASK_STATE_AUTH_REQUIRED
```
- `COMPLETED/FAILED/CANCELED/REJECTED` = **terminal**; stream closes.
- `INPUT_REQUIRED` and `AUTH_REQUIRED` = **interrupted** states (stream also closes).

**Multi-turn / input-required** (source: https://a2a-protocol.org/latest/tutorials/python/7-streaming-and-multiturn/ and §3.4.3):
- Agent asks for more input by transitioning the task to `TASK_STATE_INPUT_REQUIRED` and putting its question in `status.message`; the stream closes.
- Client continues by sending a new `Message` **with the same `taskId` and `contextId`** → the same task resumes.
- `if both are provided, they have to match` (Message doc, definitions); agent "MUST reject messages containing mismatching `contextId` and `taskId`."
- `message/send` blocking behavior is governed by `return_immediately`: if `false` (default) "the operation MUST wait until the task reaches a terminal ... or interrupted (`INPUT_REQUIRED`, `AUTH_REQUIRED`) state before returning" (definitions).

### 1.4 What A2A explicitly does NOT solve

1. **Transport/interaction-level only, not trust.** "Identity information is handled at the protocol layer, not within A2A semantics." A2A defers to TLS + declared `securitySchemes`. (§7, https://a2a-protocol.org/latest/specification/)
2. **No self-defined authorization semantics.** Verbatim:
   > "The A2A protocol does not define the scope, representation, validity, or revocation semantics of the authorization decision or credential obtained in response to this state."
   (§7.6.4)
   And: "Authorization boundaries are defined by each agent's authorization model, not prescribed by the protocol." (§13.1)
   Authz beyond "declare a scheme in the Agent Card" is agent-defined: "Authorization models are agent-defined and MAY be based on: User identity ... Organizational roles ... Custom authorization logic." (§13.1)
3. **No per-message sender identity / no signed messages.** Only `role` (user/agent). JWS signing exists for the Agent Card (§8.4), not for messages.
4. **No provenance-in-UI concept.** A2A defines no UI representation, no "who is displayed as the speaker in a transcript" field. Attribution is a rendering concern left entirely to the client. (Consistent with the §1.5 "Opaque Execution" principle: agents need not expose internals.)
5. **No "silent" delivery.** A Message is modeled as initiating/continuing a Task; there is no first-class "context-only, do not start a turn" message type. `metadata`/`extensions` are the only escape hatch.
6. **No built-in "sender = the authenticated principal" binding.** The spec requires the *server* to authenticate requests (§7.4) but does not require that the authenticated principal be recorded on the Message.

## 2. ACP — Agent Client Protocol (the Zed one)

Primary docs: https://agentclientprotocol.com/get-started/introduction · https://agentclientprotocol.com/protocol/overview

> **Naming caveat (UNVERIFIED for disambiguation only):** "ACP" is overloaded. Blogs (e.g. Camunda, https://camunda.com/blog/2025/05/mcp-acp-a2a-growing-world-inter-agent-communication/) use "ACP" for IBM Research's *Agent Communication Protocol*. **This brief covers the Zed Agent Client Protocol** at `agentclientprotocol.com`, which is a different thing.

### 2.1 Scope: agent ↔ client (editor), NOT agent ↔ agent

Verbatim (https://agentclientprotocol.com/get-started/introduction):
> "The Agent Client Protocol (ACP) standardizes communication between code editors/IDEs and coding agents and is suitable for both local and remote scenarios."
> "ACP assumes that the user is primarily in their editor, and wants to reach out and use agents to assist them with specific tasks."

- Agents "typically run as subprocesses of the Client" (https://agentclientprotocol.com/protocol/overview).
- Local agents: JSON-RPC over stdio; remote agents: HTTP/WebSocket.
- "The protocol re-uses the JSON representations used in MCP where possible, but includes custom types for useful agentic coding UX elements, like displaying diffs." (introduction) — note the explicit MCP lineage, but the *axis* is agent↔editor.
- Two roles only: **Client** (provides "the interface between users and agents. They are typically code editors (IDEs, text editors)") and **Agent** ("programs that use generative AI to autonomously modify code"). There is no peer-agent role. (overview)

### 2.2 Session model & prompt turns

Sessions (source: https://agentclientprotocol.com/protocol/session-setup):
- `session/new` → agent returns `sessionId`; `cwd` (absolute) sets filesystem context; client passes `mcpServers` for the agent to connect to.
- `session/load` (requires `loadSession` capability) replays history via `session/update`; `session/resume` (v2, `sessionCapabilities.resume`) restores without replay; `session/close` cancels + frees.

Prompt turn (source: https://agentclientprotocol.com/protocol/prompt-turn):
- `session/prompt` (v1) carries the user message; the agent reports output through **`session/update` notifications**, then responds with a `stopReason` (`end_turn`, `max_tokens`, `max_turn_requests`, `refusal`, `cancelled`).
- **ACP v2 changed the semantics of the prompt response** (source: https://agentclientprotocol.com/protocol/v2/migration): "The `session/prompt` response no longer ends the turn. It acknowledges acceptance... acceptance means insertion ... returns the `messageId`." Foreground lifecycle is now reported via `state_update` (`running` / `idle` / `requires_action`) and the stop reason moved there.
- Cancel: `session/cancel` (notification), no response expected.

### 2.3 How ACP represents who is speaking

ACP does **not** use an A2A-style `role` enum. It distinguishes speakers by the **variant of the `sessionUpdate` notification**. Verbatim from the v2 `SessionUpdate` schema table (https://agentclientprotocol.com/protocol/v2/prompt-lifecycle):

| `sessionUpdate` value | Description |
| --- | --- |
| `user_message_chunk` | "A streamed chunk of a user message." |
| `user_message` | "Creates or updates a user message identified by `messageId`." |
| `agent_message_chunk` | "A streamed chunk of the Agent's response." |
| `agent_message` | "Creates or updates an Agent message identified by `messageId`." |
| `agent_thought_chunk` | "A streamed chunk of the Agent's reasoning." |
| ... (plus `tool_call_update`, `plan_update`, `state_update`, `session_info_update`, `usage_update`, `notice`, etc.) | |

- Messages are keyed by an agent-owned opaque `messageId`: "`user_message`, `agent_message`, and `agent_thought` updates are upserts keyed by `messageId`."
- The three speaker categories are **user**, **agent**, and **agent-thought** — answered in-band, distinct from A2A's two-value `role`.
- v1 was lower-case only (`user_message_chunk`, `agent_message_chunk`, ...); v2 keeps those (messageId now required) and adds whole-message upserts (migration, https://agentclientprotocol.com/protocol/v2/migration).
- There is **no sender id / no auth-principal** on a message either — identity is the *endpoint* (the editor) plus the speaker category. Auth is a separate `authenticate` step at init (overview).

## 3. MCP — Model Context Protocol

Primary docs: https://modelcontextprotocol.io/docs/learn/architecture · https://modelcontextprotocol.io/docs/learn/server-concepts

### 3.1 Scope: agent ↔ tool/resources (and client primitives)

Verbatim (https://modelcontextprotocol.io/docs/learn/architecture):
> "MCP focuses solely on the protocol for context exchange—it does not dictate how AI applications use LLMs or manage the provided context."

Participants: **MCP Host** (AI app, e.g. Claude Code), **MCP Client** (one per server), **MCP Server** ("A program that provides context to MCP clients"). Two layers: data layer (JSON-RPC 2.0; tools/resources/prompts/notifications) and transport layer (stdio; Streamable HTTP with optional SSE).

Server primitives (the tool axis): **Tools** ("Executable functions that AI applications can invoke to perform actions"), **Resources** ("Data sources that provide contextual information"), **Prompts** ("Reusable templates").
Client primitives: **Sampling** (`sampling/createMessage`), **Elicitation** (`elicitation/create`), **Logging**.
Cross-cutting: **Tasks (Experimental)**.

Control model (https://modelcontextprotocol.io/docs/learn/server-concepts): Tools are "model-controlled"; Resources "application-driven"; Prompts "user-controlled."

### 3.2 MCP is NOT the agent↔agent axis

MCP's own docs frame it as context/tool exchange; the peer-communication axis is A2A's, verbatim:
> "An agentic application might use A2A to communicate with other agents. Inside, each agent uses MCP to work with its own tools and resources."
> — https://a2a-protocol.org/latest/topics/a2a-and-mcp/

That said, MCP *can* be bent toward inter-agent use — it is a pattern, not the protocol's declared scope:
- AWS documents wrapping an agent as an MCP server for inter-agent communication: https://aws.amazon.com/blogs/opensource/open-protocols-for-agent-interoperability-part-1-inter-agent-communication-on-mcp/ ("MCP already provides the core infrastructure needed for agents to communicate... Multi-agent communication can take on a variety of different patterns").
- The MCP project itself treats the "MCP vs A2A" overlap as an **open question**, not settled scope: https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/1108 ("MCP is bidirectional but in a limited and structured way, whereas A2A is designed for peer-level agent communication.").
- **UNVERIFIED:** I found no *normative* MCP spec sentence that says "MCP is not for agent-to-agent." The "not agent↔agent" position is the documented *intent/scope* (host↔tool) shared by MCP and A2A docs, plus open community debate — not a MUST NOT in the spec.

### 3.3 Three-axis summary (the decision table)

```
A2A  : agent  <-> agent          (peer; application-level task/message protocol)
ACP  : agent  <-> client/editor  (IDE hosts agent; UX-oriented, JSON-RPC)
MCP  : agent  <-> tool/context   (server exposes tools/resources/prompts to host)
```

## 4. Which protocol fits a PEER SESSION WRITE, and why

**Scenario:** the `dsh-openai-live` plugin lets a voice model write into a coding-agent session with two verbs: SILENT NOTE (model-facing context, does not start a turn) and VISIBLE SAY (starts a turn, attributed to the voice, shown in transcript). Question: which of A2A / ACP / MCP is the appropriate model for *one agent session writing a message into a sibling agent session*?

**Answer: A2A is the right axis.** Rationale, tied to §0–§3:

1. **Counterpart is a peer agent, not an editor and not a tool.** A2A is the only one of the three explicitly agent↔agent ("Standardizes how independent, often opaque, AI agents communicate and collaborate as peers" — https://a2a-protocol.org/latest/topics/a2a-and-mcp/). ACP's counterpart is the IDE/client; MCP's counterpart is a tool/context server. Both are the wrong axis.
2. **A2A has the exact provenance carriers a session-write needs.** `contextId` (conversational session grouping) + `taskId` (unit of work) + `referenceTaskIds` + `metadata` map cleanly onto "write into sibling session X, replying to / referencing session Y." (§3.4.1–3.4.3)
3. **A2A models turn-taking and multi-turn explicitly** (`INPUT_REQUIRED` + resume on same `taskId`/`contextId`) — the right vocabulary for "starts a turn" vs "does not start a turn."
4. **A2A has a clean place to hide the mechanism and carry attribution** — `metadata` and declared `extensions` — without inventing a wire format.

**But two honest gaps the plugin must design around (both decision-relevant):**

- **A2A has no native "silent note."** Every A2A `Message` is modeled as initiating/continuing a `Task`; there is no first-class context-only, non-turn-starting message. SILENT NOTE has no exact A2A equivalent and must be expressed as `metadata`/an extension. (§1.4 item 5)
- **A2A has no per-message sender identity and no provenance-in-UI.** Only `role` (`ROLE_USER`/`ROLE_AGENT`) exists on a Message; identity is explicitly "handled at the protocol layer, not within A2A semantics." "Attributed to the voice" is therefore **not** an A2A primitive — the plugin must carry voice attribution in `metadata`/extension and render it client-side. (§1.2, §1.4 items 3–4)

**Why not the others:** ACP is client↔editor, so using it would mean the voice model masquerades as the editor/client — the wrong relationship, and ACP's speaker model (`user_message` / `agent_message` / `agent_thought` via `sessionUpdate`) is a per-client transcript, not peer-to-peer (§2). MCP would require wrapping the target session as a tool/resource the caller's LLM invokes — workable (AWS pattern) but the caller becomes a *tool caller*, not a peer, and MCP is "designed to be the caller-LLM-driven" tool axis, not peer session messaging (§3.2).

**Recommended shape (design note, not spec):** model the peer write as an A2A `Message` on the target session's `contextId`/`taskId`, with `role: ROLE_AGENT`, a `metadata` block carrying `{ voice_actor, silent|visible, attribution }` (or a declared `dsh-openai-live` A2A extension), and use `extensions` to declare it. SILENT vs VISIBLE then becomes a metadata discriminator the receiving session honors (VISIBLE ⇒ insert as a turn; SILENT ⇒ context-only), since A2A itself defines no such switch.
