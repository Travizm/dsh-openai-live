# 04 — How products encode message PROVENANCE in the UI

**Question:** how do shipping products render "this message came from another agent / an automated actor — not from you, and not from the model's own output"?

**Method:** fetched vendor docs, REST/API schemas, product help centres and changelogs directly (`web_extract` + search). Every claim below carries a source URL. Anything I could not confirm on a vendor-controlled page is listed in the **UNVERIFIED** section at the bottom and is not relied on in the synthesis.

**Date of research:** 2026-10-15.

---

## 0. The four orthogonal signals products actually use

Across every product surveyed, provenance is conveyed by a small set of independent, composable signals. They are orthogonal — a mature product uses *several at once*:

| # | Signal | What it is | Examples |
|---|---|---|---|
| **S1** | **Sender-type field on the message object** | A machine-readable enum on the record itself | Slack `bot_id` / `app_id` / `subtype`; Intercom `author.type`; Sunco `role`; Teams `from.role`; Discord `webhook_id`; GitHub GraphQL `__typename: "Bot"` |
| **S2** | **Distinct sender identity in the transcript** | The message is attributed to a *different visible actor* (name + avatar), not to the human | Slack bot profile; Teams agent name; Devin in Slack; ChatGPT `author.name` |
| **S3** | **Inline content label / badge on the message** | A chip adjacent to the author name or message | Teams "AI generated"; Zendesk "Generated by AI"; Intercom "AI Agent"; Salesforce sparkle; Slack `APP` badge |
| **S4** | **Banner / footer disclosure** | A block-level strip, once per group/conversation, or a persistent footer | Intercom email footer "This answer was composed by …"; Zendesk grouped label; Outlook "?"/`via`; Gmail "Mailed by / Signed by" |

**The single most decision-relevant pattern:** the strong products have **both** a structural field (S1, survives export/API/automation) **and** a human-visible affordance (S2/S3, survives a screenshot). Products that only do the visual label lose provenance the moment the message is exported to JSON. Products that only do the field leave the human unable to tell who spoke.

**Second pattern:** the visual label is attached to the **author identity**, not repeated per message. Zendesk explicitly redesigned for this — see §1.2.

## 1. Human-in-the-loop agent handoff (support / ops)

### 1.1 Zendesk — AI agent ("Generated by AI") + role-by-side convention

**Affordance**
- Web Widget messaging: the AI disclosure is **a label on the AI agent's name**, and it appears **once per group of messages** — not on every bubble. Before the redesign it was a footer disclaimer on *every* AI message.
- In the agent-side **conversation log** transcript, speaker role is encoded **by the side of the transcript**: *"The icon appears to the left of AI agent messages and to the right of user messages."* The icon opens a per-message detail pane.
- Per-message detail pane is **named by role**: it is called **"Message overview"** for a user message, and **"AI agent message overview"** for an AI agent message. The latter exposes `Use case`, `Plan` (the reasoning), `Procedure step`, `Response before customization`, `Active instructions`, and `Personalization` (`AI agent name`, `Company name`, `Tone`, `Answer length`).
- AI-agent-only conversations become **read-only tickets** with explicit visual identifiers: bot icon in the ticket tab, an **"AI agent" badge in the ticket header**, greyed-out properties panel, hidden composer and macros menu, and a footer note saying it is an AI agent ticket. The Assignee column shows a bot icon in views/search.
- The **Resolution type field** literally carries the value **`Automated`**, and the events view carries a system entry recording the date/time of the automated resolution.

**Fields**
- Conversation object: `Status` ∈ {`Unassisted`, `Assisted escalation`, `Automated resolution`}; **`Resolution tier`**; `Resource usage` ∈ {`Dialogue`, `Generative reply`, `Procedure`, `Knowledge answer`}; `Test conversation`; `Platform conversation ID` (CRM correlation); `Labels`; `Use cases`; `Segments`; `BSAT`.
- Ticket object: `Resolution type` = `Automated`; assignee carries a bot icon and a **`Contributor`** role on the AI agent's profile.
- Message-level: presence/absence of the detail icon and the pane name carry the role.

**Sources**
- https://support.zendesk.com/hc/en-us/articles/10458073496090-Announcing-the-Generated-by-AI-disclosure-redesign-in-Web-Widget *(the redesign: label on agent name, once per group)*
- https://support.zendesk.com/hc/en-us/articles/8357749580186-Reviewing-conversation-logs-for-AI-agents *(icon left/right of AI vs user messages; pane names; Resolution tier; Resource usage)*
- https://support.zendesk.com/hc/en-us/articles/8854858307610-What-are-the-conversation-statuses-for-AI-agents *(status enum)*
- https://support.zendesk.com/hc/en-us/articles/9204149016346-Understanding-AI-agent-tickets-for-AI-agent-only-conversations *(ticket-level visual identifiers, `Automated` resolution type, `Contributor` role)*

**Takeaway for us:** Zendesk treats *"AI spoke here"* as a property of **the conversation and the ticket**, not only of the individual message. It also proves a useful nuance: **the transcript-side convention (left/right + icon) is different from the end-user-side convention (label on name)**. Two audiences, two affordances, same underlying role data.

### 1.2 Intercom — Fin AI Agent

**Affordance**
- Messenger: a **built-in "AI Agent" label after the AI agent's name** on the message card. Configurable: `Fin AI Agent > Fin settings > Identity > "Show AI Agent label in Messenger"` (on by default for Fin users up to 2025-07-10; off by default for new customers).
- Email (Zendesk ticket / Salesforce case replies): a persistent footer directly below the AI's signature — **"This answer was composed by [AI Agent name], [Workspace name]'s AI Agent."** Toggle: `Fin AI Agent > Fin settings > General > "Show 'Composed by AI' in email footer"` (on by default).
- When the label is switched off, Intercom's documented fallback is an **intro message in-conversation** ("Hi there! You're speaking with [AI Agent name] AI Agent…") — i.e. **disclosure moves from per-message to once-per-conversation**.
- Intercom states the previous behaviour explicitly: Fin *"always appeared as Fin 'AI Agent'"* and *"its responses were automatically marked as an **AI Answer**"* — and they **removed** the `AI Answer` label in favour of configurable disclosure.

**Fields**
- Conversation part object (REST): `author.type` ∈ **`user` | `admin` | `bot`** plus `author.id`; `part_type` ∈ {`comment`, `note`, `note_and_reopen`, `assignment`, `assign_and_unsnooze`, …}; `app_package_code`.
- `assigned_to.type` ∈ {`admin`, `team`, `bot`} (`nobody_admin` when unassigned).
- Dataset export: "the type of agent rated (**teammate or Fin AI Agent**)".
- Important documented semantics: *"Bots and campaigns send messages **on behalf of** Admins or Teams."* — i.e. Intercom's model is that an automated actor can *impersonate* an admin identity at the message layer, and the only structural tell is `author.type`.

**Sources**
- https://www.intercom.com/help/en/articles/11712008-ai-agent-disclosure
- https://intercom.help/fin4all/en/articles/11847955-what-is-ai-agent-disclosure
- https://www.intercom.com/changes/en/96733-let-your-customers-know-they-re-speaking-with-an-ai-agent
- https://developers.intercom.com/docs/references/2.13/rest-api/api.intercom.io/models/conversation_part *(author.type)*
- https://developers.intercom.com/docs/references/2.6/rest-api/conversations/conversation-model *(author.type for part; "Bots and campaigns send messages on behalf of Admins or Teams"; part_type enum)*

### 1.3 Microsoft Teams (Bot Framework) — the strongest field-level precedent

This is the closest structural analogue to what `dsh-openai-visual` needs, because Teams ships **both** a machine-readable entity and a non-customisable visual label.

**Affordance**
- With `addAiGenerated()` / `AddAIGenerated()`, the agent's message shows an **"AI generated" label next to the agent's name**. Hovering it shows the disclaimer **"AI-generated content may be incorrect."**
- Crucially: *"The AI label and disclaimer **can't be customized** for AI-powered agents."* (A community issue asking to customise the text was filed and the docs are explicit that the only allowed value is `AIGeneratedContent`.)
- Available in personal chats, group chats, channels, and in GCC / GCC High / DoD.
- Separate, additive affordances: **citation** (in-text `[n]` + hover pop-up + modal), **feedback buttons** (👍/👎 in the message footer), **sensitivity label** (a **shield icon** in the message, hover for the description).

**Fields — the AI provenance entity**
```jsonc
entities: [
  {
    "type": "https://schema.org/Message",
    "@type": "Message",
    "@context": "https://schema.org",
    "additionalType": ["AIGeneratedContent"]   // <- the provenance marker
  }
]
```
- `additionalType` — *"Indicate that the content was generated by AI."* Only allowed value: `["AIGeneratedContent"]`.
- Sibling entity members: `citation[]` (`@type: Claim`, `position`, `appearance.{@type: DigitalDocument, name, url, abstract, text, keywords, encodingFormat, image}`), `usageInfo` (`@type: CreativeWork`, `name`, `description`) for the sensitivity label.
- Message/Activity-level sender role: **`from.role`** on the `ChannelAccount` — *"Role of the entity behind the account (Example: User, Bot, etc.). Possible values include: **'user', 'bot', 'skill'**."*
- Activity `type` enum includes **`handoff`**, and `deliveryMode` includes `ephemeral` / `expectReplies`.
- Bot Framework channel-account `RoleTypes` enum is documented as exactly `'user', 'bot', 'skill'`.

**Sources**
- https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/bot-messages-ai-generated-content
- https://learn.microsoft.com/en-us/javascript/api/@microsoft/agents-activity/aientity?view=agents-sdk-js-latest *(`additionalType: ["AIGeneratedContent"]`)*
- https://learn.microsoft.com/en-us/javascript/api/botframework-schema/channelaccount?view=botbuilder-ts-latest *(`role` ∈ user/bot/skill)*
- https://learn.microsoft.com/en-us/javascript/api/botframework-schema/?view=botbuilder-ts-latest *(`RoleTypes` enum)*
- https://learn.microsoft.com/en-us/dotnet/api/microsoft.teams.api.activities.activity?view=msteams-sdk-dotnet-latest *(`AddAIGenerated()` method on the activity)*
- https://github.com/microsoft/botframework-sdk/issues/6673 *(community confirmation that the value is not customisable)*

**Takeaway for us:** the `additionalType: ["AIGeneratedContent"]` pattern is a **boolean-ish provenance flag carried on the message entity itself**, with the *rendering* (label text, tooltip) owned by the platform and deliberately not customisable. That is exactly the shape a plugin should mirror if the host application must be able to render the chip itself.

### 1.4 Salesforce / Agentforce / Einstein

**Affordance**
- **Sparkle icons** are the platform-wide AI indicator. Designed as two variants: *three sparkles* = an AI-powered button that opens Einstein/Copilot; *single sparkle* = **"the content has been generated by AI, and no human has modified it"**, with a hover tooltip.
- The single sparkle "can pair with other icons (e.g. pencil for AI-assisted editing, refresh for content regeneration)".
- Admin-side: AI-powered quick actions are identifiable **by the sparkles icon**; AI-powered fields are denoted **by the orange Einstein icon** and show a wand icon on the record page.
- Salesforce's own trust-patterns page states the policy position: *"our UI element clearly and transparently discloses when content is AI-generated. The Einstein 'sparkles' icon helps indicate and alert the user…"* and *"our AI Acceptable Use Policy requires that customers must disclose when end users are interacting directly with an automated system."*
- Audit/reporting side: AI interactions are captured in event logs; "real-time check marks are also displayed for processes that AI has completed".

**Fields**
- Einstein Trust Layer exposes an **audit trail**, **feedback**, toxicity detection and AI monitoring as first-class named capabilities — the field-level detail is behind the trust-layer surface rather than on the message object.
- Record page: the field ↔ prompt-template **page-layout association** is the switch that turns the sparkle on; without it the field behaves as a normal field. (Provenance is thus *configuration-derived metadata*, not a per-message field.)

- https://admin.salesforce.com/blog/2025/revolutionize-record-pages-ai-powered-agent-shortcuts-are-here *("You can tell a quick action is AI-powered by the sparkles icon")*

### 1.5 Decagon and Sierra

Both are AI-agent vendors whose *customer-facing* transcripts are rendered inside a third-party helpdesk (Zendesk / Intercom / Salesforce), so the visible label is normally the helpdesk's (§1.1–1.2). What they contribute is the **handoff-payload design** — the fields that travel *with* a conversation when control changes actor. This is directly analogous to "an automated actor writes into a session".

**Decagon — handoff schema (documented design guidance)**
- Named payload elements: **Objective and current state**; **Evidence and provenance** (each fact tagged with its origin — KB article with identifier, tool response with timestamp, or **"unverified customer statement"**); **Confidence** (score on intent and on each material conclusion); **Authorization scope** (explicit, not inferred); exclusions (what was already tried).
- Explicit statement of the design tension we face: *"a schema that is documented but not enforced is a convention, and conventions decay"* — validation at the boundary, required fields, types correct, enums in range.
- Also: **agent-to-human handoff has to *render*** — "a support representative cannot read a hundred-field object mid-conversation, so the schema needs a presentation layer that surfaces intent, verification status, what was tried, and the recommended next action within seconds." And: the customer *"must be aware"* — a silent transfer is called out as a failure mode.
- Decagon's customer-facing commitment: *"We believe in transparency. Customers know they are talking to an AI, and a seamless handoff to a human agent is always an option."*

**Sierra**
- Sierra's public material documents supervisor/monitor architecture (real-time supervision and post-hoc review with every flagged conversation linking to its transcript) but does not publish a message-level disclosure field. Its configurable surface is agent identity: **"Give your AI agent a name and voice, craft its welcome message, and align its look with your brand—logo, colors"** — i.e. provenance-by-distinct-identity rather than provenance-by-label.
- Sierra states AI safety uses "secondary agents" (supervisors) — relevant as a precedent for *an agent reading another agent's output*, not for user-facing provenance.

**Sources**
- https://decagon.ai/glossary/what-is-an-agent-handoff-schema
- https://decagon.ai/glossary/what-is-an-ai-agent-handoff
- https://decagon.ai/blog/conversational-ai-for-customer-experience
- https://sierra.ai/blog/confidence-in-every-conversation
- https://sierra.ai/product/agent-studio
- https://sierra.ai/blog/ai-agents-guide

## 2. Multi-agent / agentic chat UIs

### 2.1 Slack — `bot_id` / `app_id` / `subtype` + the `APP` badge

This is the canonical reference implementation for our problem: a single message object that says *who really sent this*, with a visible badge.

**Affordance**
- Bot/app messages carry a visible **`APP` badge** next to the app name (see UNVERIFIED note below on official documentation of the badge *text*; the mechanism is fully documented).
- Slack's own security/consent framing is explicit about the *intent* behind the distinction:
  - `chat.postMessage`: *"Apps can publish messages that appear to have been created by a user in the conversation. The message will be attributed to the user and show their profile photo beside it. This is a powerful ability and must only be used when the user themselves gives permission… Your app should only use this feature in response to an inciting user action. **It should never be unexpected or surprising to a user that a message was posted on their behalf, and it should be heavily signposted in advance.**"*
  - The `as_user: false` path produces `"bot_messages"` with authorship attributed to the app's name and icons.
- Slack also documents that **bot users have their own presence** (grey dot when `away`, green dot when `active`, `always_active` in the profile) — a second, ambient provenance cue.

**Fields — the Slack message object (the field set to copy)**

| Field | Meaning | Provenance role |
|---|---|---|
| `subtype` | e.g. `"bot_message"` (enum also includes `channel_join`, `file_share`, `me_message`, `thread_broadcast`, `tombstone`, `reminder_add`, `pinned_item`, …) | **Type discriminator** |
| `bot_id` | *"The bot ID if this message was posted by a bot. Bot IDs begin with `B`."* | **Automated sender is a bot** |
| `bot_profile` | `{ id, deleted, name, updated, app_id, icons{image_36,image_48,image_72}, team_id }` | **Bot's display identity** |
| `app_id` | *"The app ID if this message was posted by an app."* | **Which app** |
| `user` | *"The user ID of the message author. User IDs begin with `U` or `W`."* | **Human/other sender** |
| `username` | Optional per-message override of the display name | **Spoofable label** (see caveat) |
| `icons` | Optional per-message icon override; `icon_url`, `icon_emoji` | **Spoofable avatar** |
| `metadata.event_type` / `metadata.event_payload` | App-attached structured metadata, invisible in the message body | **Machine-readable sidecar** |
| `client_msg_id` | Client-assigned dedupe id | Origin differentiation |
| `edited.{user,ts}` | Who/when last edited | Post-hoc provenance |
| `assistant_thread` | Present on assistant-surface threads | Surface discriminator |
| `app_context` | App-context-changed context | Surface discriminator |
| (streaming) `streaming_state` ∈ `'in_progress' \| 'completed' \| 'errored'` | On `BotMessageEvent` | **In-flight automated output** |

- Slack's documented detection rule, verbatim: *"With current Slack apps, also known as granular bot permissions (GBP) apps, you can detect if a message was sent by a bot by **the presence of the `bot_id` and `bot_profile` fields in the event payload**."*
- TypeScript types (`BotMessageEvent`) confirm the shape: `subtype: 'bot_message'`, `bot_id: string` (required), `username?`, `icons?`, and — importantly — **`user?: string` is optional**, with the SDK comment *"TODO: is a user really optional? likely for things like IncomingWebhook authored messages"*.
- **Caveat that matters a lot for us:** `username` and `icons` are **overrides supplied by the sender**. Slack's own doc says *"Some `bot_message` events also include `username` or `icons` properties. If present, these override the default username or icon for this bot."* The `chat:write.customize` scope is what enables this, and Slack's guidance is that it "should be heavily signposted". **So a visible name/avatar is spoofable; `bot_id` / `app_id` / `subtype` are not.**
- Slack's Agents platform (2025+) adds `assistant:write` ("*Allow your Slack app to act as an **App Agent***"), agent sessions with `agents.sessions.setStatus` / `agents.sessions.rename`, and an `agent_view` experience where the agent's conversations live in the Messages tab.

**Sources**
- https://docs.slack.dev/reference/events/message/bot_message/ *(`subtype`, `bot_id`, `username`, `icons`, detection rule)*
- https://docs.slack.dev/reference/methods/chat.postMessage *("Sending messages as other entities", `chat:write.customize`, `username`/`icon_url`/`icon_emoji`, legacy `as_user`, the "never unexpected or surprising" rule)*
- https://apis.io/schemas/slack/slack-message/ *(full field table incl. `bot_id` "begin with B", `app_id`, `bot_profile`, `metadata.event_type`/`event_payload`, `client_msg_id`)*
- https://github.com/slackapi/node-slack-sdk/blob/main/packages/types/src/events/message.ts *(`BotMessageEvent` shape; `user?` optional; `streaming_state`)*
- https://github.com/slackapi/java-slack-sdk/blob/main/slack-api-model/src/main/java/com/slack/api/model/Message.java *(`appId`, `botId`, `botProfile`, `icons`, `displayAsBot`)*

### 2.2 Discord — `webhook_id` vs `bot` vs `application_id`

**Affordance / field semantics — unusually clean, and worth copying.**
- The message `author` object is *"not guaranteed to be a valid user"*: *"The author object follows the structure of the user object, but is only a valid user in the case where the message is generated by a **user or bot user**. If the message is generated by a **webhook**, the author object corresponds to the **webhook's id, username, and avatar**. You can tell if a message is generated by a webhook by checking for the **`webhook_id`** on the message object."*
- Fields: **`webhook_id?`** (snowflake — "if the message is generated by a webhook, this is the webhook's id"); **`application_id?`** ("if the message is an Interaction or application-owned webhook, this is the id of the application"); **`interaction_metadata?`** ("Sent if the message is sent as a result of an interaction"); `interaction?` (deprecated in favour of `interaction_metadata`); `application?` (partial application object); `type` (integer message-type enum, incl. `REPLY`=19, `CHAT_INPUT_COMMAND`=20, `CONTEXT_MENU_COMMAND`=23); `flags` bitfield (incl. `EPHEMERAL` `1<<6`, `LOADING` `1<<7`, `SUPPRESS_NOTIFICATIONS` `1<<12`, `IS_VOICE_MESSAGE` `1<<13`).
- Discord's **search API** exposes sender class as a first-class filter: `has=user | bot | webhook` — *"Return messages sent by user accounts / bot accounts / webhooks"*.
- `message_snapshots[]` carries *"a minimal subset of fields in a message (e.g. `author` is excluded)"* — i.e. the platform deliberately **strips the author** when echoing content.

**Sources**
- https://docs.discord.com/developers/resources/message *(webhook_id; application_id; interaction_metadata; author footnote; search `has` types; flags)*
- https://github.com/discordjs/discord-api-types/blob/main/payloads/v10/message.ts
- https://discord.js.org/docs/packages/discord-api-types/main/APIMessage:Interface

**Takeaway for us:** Discord's model — *the `author` field may be a display fiction, and the authoritative origin is a separate id field* — is the cleanest statement of the design rule we should adopt: **never derive provenance from the rendered name; always carry an explicit origin id.**

### 2.3 GitHub — bot actors, `__typename: "Bot"`, `performed_via_github_app`

**Affordance**
- Automation acts as an **App bot account** displayed as `<app-slug>[bot]`, visually distinct from a human account.
- Co-authorship trailers (`Co-authored-by: Name <email>`) are disclosed in commit messages when an AI tool injects them — GitHub *recognises* the trailer, but "whether an AI tool adds such a trailer — and whom it names — is product and workspace policy, **not an identity guarantee**".

**Fields**
- GraphQL: the `Actor` interface is *"Represents an object which can take actions on GitHub. Typically a User or Bot."* Types implementing it include **`User`**, **`Bot`** (*"A special type of user which takes actions on behalf of GitHub Apps"*), **`App`**, and Mannequin. Discrimination is by **`__typename`**.
- **Critical footgun, documented in a real patch:** REST and the UI return the suffixed login (`dependabot[bot]`); GraphQL returns the **bare** login (`dependabot`) and identifies it only via `__typename: "Bot"`. Code that pattern-matched `*[bot]` against GraphQL data silently matched nothing.
- REST: check runs carry `check_suite.app` (a **GitHub app** object) and `check_suite.pull_requests[].head`, plus **`performed_via_github_app`** on many objects — an explicit *"this action was performed via an app"* field.
- REST checks write scope: *"Write permission for the REST API to interact with checks is only available to **GitHub Apps**. OAuth apps and authenticated users can view check runs and check suites, but they are not able to create them."*

**Sources**
- https://docs.github.com/en/enterprise-server@3.13/graphql/reference/objects *(`Bot`: "A special type of user which takes actions on behalf of GitHub Apps"; implements Actor, Node, UniformResourceLocatable)*
- https://docs.github.com/en/enterprise-server@3.13/graphql/reference/interfaces *(`Actor`: "Represents an object which can take actions on GitHub. Typically a User or Bot.")*
- https://docs.github.com/en/rest/checks/runs *(`check_suite.app`, `performed_via_github_app`, GitHub-App-only write)*
- https://github.cnmirror.space/anthropics/claude-code-action/pull/1616 *(REST `dependabot[bot]` vs GraphQL `dependabot` + `__typename: "Bot"`)*
- https://zylos.ai/research/2026-09-02-github-apps-machine-identity-ai-agent-git-workflows/ *(App bot account `<slug>[bot]`, separate numeric bot user id vs App id, co-authorship trailer not an identity guarantee)*

### 2.4 Claude Code / Claude Agent SDK — subagent output as a *sidechain*

Directly relevant: this is the reference for "a second model produced this text inside my session".

**Fields (Claude Agent SDK, official)**
- `SDKUserMessage` carries **`parent_tool_use_id`** (typed `null` in the documented example) — the official, supported mechanism for associating a message with the tool call that spawned it.
- Message stream types: `type` ∈ `user` | `assistant` | `result` | `system`; `result` has `subtype` (e.g. `success`, `error_max_turns`) and `result`.
- Session/list APIs: `SDKSessionInfo` exposes `sessionId`, `summary`, `customTitle`, `firstPrompt`, `gitBranch`, `cwd`, `tag`, `createdAt`.

**Fields (on-disk JSONL transcript — community-documented, see UNVERIFIED)**
- `isSidechain: true` marks subagent / branch entries.
- `agentId` identifies the subagent that produced a line; the subagent's own transcript lives at `<session>/subagents/agent-*.jsonl`.
- `attributionAgent` — the subagent *type* a sidechain line ran under (e.g. `general-purpose`); one parser explicitly appends it to the agent name so *"a subagent turn is distinguishable from a main-thread one."*
- `parentUuid` / `uuid` form the message tree (interrupts and retries branch); `isMeta` marks non-conversational user records; `forkedFrom` marks copied branch prefixes.
- One assistant API response can be persisted as **several** `assistant` lines sharing one `message.id` — deduplicate by `message.id`.

**UI behaviour (from filed bug reports — this is the useful part)**
- Main thread shows a **collapsed one-line summary** for a subagent dispatch, e.g. `Done (10 tool uses · 45.6k tokens · 2m 2s)`. Neither the dispatch prompt (~5,022 chars) nor the returned result (~15,587 chars) was expandable — the author notes the data is intact in the JSONL and *"it is purely a rendering/visibility issue"*.
- A user request against the VS Code panel asks for exactly the right pattern: *"one expandable block per Task run, headed by the subagent type and task description"*, plus an "agents in flight" strip (status / tokens / elapsed). The relevant data already exists: messages arrive tagged with `parent_tool_use_id`, and a `subagentTasks` map holds description/status/recent tools/token usage/duration.
- **The failure mode to avoid:** on iOS, tapping into a subagent showed the *parent's* `Task` tool call — including launcher metadata the model was explicitly told to treat as internal and never surface ("Async agent launched successfully. - Third-party renderers converge on the same shape: "Render sub-agent OUTPUT inside timeline … as a **labeled OUTPUT section** inside the orange-bordered sub-agent timeline, with markdown rendering and a copy-to-clipboard button."

### 2.6 Devin — an agent as a first-class Slack participant

**Affordance**

### 2.7 ChatGPT / custom GPTs / connectors

**Affordance / fields (from the export format)**

A separate request asks for the GPT's logo in chat history so users stop manually tagging titles.
- Related: `metadata.is_visually_hidden_from_conversation` is the exported-format name for exactly the "model-facing, hidden" category that our **SILENT NOTE** verb needs.

**Two design lessons that appear repeatedly:**
1. **Warnings must not accumulate in the model's context.** Devin's harness injects per-message notes into the *prompt build*, not the session history: "These warnings never pile up in the session's context… Otherwise, a long thread would bury the conversation under a mountain of identical warnings." This maps exactly onto SILENT NOTE (persistent, model-facing) vs a per-turn provenance wrapper (transient).
2. **Impersonation-capable surfaces get a "never surprising" rule.** Slack's `chat:write.customize` guidance — *"It should never be unexpected or surprising to a user that a message was posted on their behalf, and it should be heavily signposted in advance"* — is the normative statement for VISIBLE SAY rendering as the human.

## 5. Synthesis for `dsh-openai-live`

Practical implications, each traced to evidence above.

1. **Carry a structural field, don't infer from text.** Slack's `bot_id`/`app_id`/`subtype`, Discord's `webhook_id`, GitHub's `__typename: "Bot"`, Teams' `additionalType: ["AIGeneratedContent"]`, Intercom's `author.type`. Fields survive JSONL export, re-render, search and automation; a visual chip does not. (§2.1, §2.2, §2.3, §1.3, §1.2)

2. **Do not trust the rendered name/avatar as provenance.** Slack explicitly lets senders override `username`/`icons`; Discord says the `author` object "is not only valid in the case where the message is generated by a user or bot user"; Intercom notes bots "send messages on behalf of Admins or Teams". The rendered byline is presentation; the origin id is truth. (§2.1, §2.2, §1.2)

3. **Use the S1+S2+S3 triple, not just one.** Every mature implementation pairs a field with a distinct *sender identity* and an *inline label*. Where a product lacked a field (ChatGPT custom-GPT attribution) users filed feature requests describing exactly the missing affordance. (§2.7)

4. **Attach the label to the author identity, once per group — not per message.** Zendesk's redesign is an explicit, sourced decision with the rationale and the rejected alternative. Teams does the same by putting "AI generated" next to the *agent's name*. (§1.1, §1.3)

5. **Non-customisable disclaimers exist and are sometimes legally motivated.** Teams: the label and disclaimer "can't be customized for AI-powered agents", value fixed at `AIGeneratedContent`. Zendesk/Intercom cite AI-Act-style transparency duties and both document a compliant fallback when the badge is disabled. If our VISIBLE SAY line is attributed to a voice/automated actor, the label should be non-suppressible. (§1.3, §1.1, §1.2)

6. **Distinguish "hidden/model-facing" from "visible" with an explicit field, and make the *absence* meaningful.** ChatGPT exports carry `metadata.is_visually_hidden_from_conversation`, and third-party exporters have to filter on it. Discord strips `author` from `message_snapshots`. Claude Code marks non-conversational user records with `isMeta`. Our SILENT NOTE needs an explicit marker, and the default (no marker) should be the visible case — never the reverse. (§2.7, §2.2, §2.6)

7. **Subagent/agent output should be a nested, collapsible, *labelled* block owned by the parent turn — never rendered as if the human said it.** Claude Code's filed bugs are a catalogue of the failure modes: collapsed one-liner with no expand affordance; drilling into a subagent showing the *parent's* tool call including bytes the model was told never to surface (`agentId`, internal directives, absolute host paths). The accepted fix pattern is a labelled block or status chip, and Cursor has moved to streaming subagent activity *under the parent's task*. (§2.4, §2.5)

8. **Give the automated actor its own identity, and let that identity be declared in-band.** Cursor subagent frontmatter (`name`, `description`, `model`, `readonly`, `is_background`); Devin's Slack app holding `app_mentions:read` + `assistant:write` and posting as `@Devin`; Teams/Copilot a distinct chat participant. Identity is the cheapest provenance signal and the one a human reads first. (§2.5, §2.6, §1.3)

9. **Provenance should also cover *actions and edits*, not only chat turns.** Excel's Show Changes pane renders "Copilot attribution cards indicating AI-generated changes"; Zendesk stamps `Resolution type = Automated` and logs a system event; GitHub carries `performed_via_github_app`. If the voice agent writes into a session, the *write* needs a stamp too, not just the utterance. (§2.8, §1.1, §2.3)

10. **Warning/noise budget is a first-class concern.** Zendesk's redesign, Devin's "never pile up in the context" rule, and Gemini's single standing disclaimer all trade per-message loudness for once-per-group or once-per-session disclosure. For a realtime voice actor that may speak often, a per-utterance banner will be tuned out within minutes. (§1.1, §2.6, §2.9)

11. **Adopt the handoff-payload vocabulary for what the model sees.** Decagon's handoff schema names the fields: objective + current state, evidence **with per-claim provenance** (including an explicit **"unverified customer statement"** category), confidence, and authorisation scope — plus the rule that an *agent-to-human* payload "has to render" while an agent-to-agent payload can stay dense. SILENT NOTE is the agent-to-agent half; VISIBLE SAY is the render half. (§1.5)

12. **Beware enum drift between two APIs for the same actor.** GitHub REST/UI say `dependabot[bot]`, GraphQL says `dependabot` + `__typename: "Bot"`; a filter written against the former silently matched nothing against the latter, and the existing test mocked a payload GraphQL never produces, so the gap was invisible. Normalise provenance at a single choke point. (§2.3)

## 7. UNVERIFIED (not relied on above)

1. **Slack's `APP` badge as a documented product string.** Slack's own developer and help docs describe the *mechanism* (bot token ⇒ message posted as the app/bot user; user token ⇒ attributed to the human) but I could not find a vendor page that names the badge text "APP". Evidence for the badge itself is third-party: https://docs.duvo.ai/user-guide/connections/slack-bot-identity (quoted in §2.1), https://stackoverflow.com/questions/50819475/, https://stackoverflow.com/questions/76151921/. Treat "APP badge" as observed-in-product, not vendor-documented.

2. **Salesforce Lightning Design System "Agentic Patterns" component spec.** https://www.lightningdesignsystem.com/2e1ef8501/p/03c548 returned no body content (JS-rendered), so any published SLDS spec for an AI/agent chip, its variants or its accessibility requirements is unconfirmed.

3. **Claude Code's on-disk JSONL schema.** Anthropic publishes the Agent SDK types but not a schema for `~/.claude/projects/**/*.jsonl`. `isSidechain`, `agentId`, `attributionAgent`, `parentUuid`, `isMeta`, `forkedFrom` come from community parsers (sources 68–71) which explicitly say the format is empirically derived and has drifted across versions. `isSidechain: true` is described by one parser as "preserved on every event but currently **informational**".

4. **Google's per-message provenance field for Gemini content.** No official Google documentation found that defines a sender-type field on a message containing Gemini-generated content (in Gmail, Docs or Chat). Gemini appears to rely on feature-level identity plus a standing disclaimer.

5. **OpenAI's message-level provenance for connectors / Apps.** The ChatGPT export format carries `author.role` and `author.name`, but no official schema is published by OpenAI for it; the field reference used here is derived. There is no documented field identifying *which* custom GPT or connected App produced a given message — the origin-icon feature requests imply the data exists internally but is not exposed.

6. **Decagon / Sierra end-user transcript rendering.** Both vendors' customer-facing transcript affordances live inside third-party helpdesks, so I found no Decagon- or Sierra-branded message label or sender-type field. Their contribution documented here is the handoff-payload schema and supervision architecture, not a UI label.

7. **Zendesk per-message icon graphics.** The help article says "The icon appears to the left of AI agent messages and to the right of user messages" but the icon's image and accessible name are not in the text; the article's screenshots were not readable via text extraction.

8. **`sender_business_bot` / `sender_chat` behaviour in practice** (Telegram) is documented in the API reference but I did not test the rendering semantics.
