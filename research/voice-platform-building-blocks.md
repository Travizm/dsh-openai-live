# Realtime voice-agent developer platforms — building blocks to learn from, adopt, or avoid

**Date:** 2026-10-15 (AEST)
**Context:** `dsh-openai-live` — a realtime full-duplex voice plugin for DeepSeek Harness (DSH). TS, 6 packages, npm, enforced per-file 100% coverage, leak scan, built-artefact smoke test, protocol canary. WebSocket + 24 kHz PCM16, `ScriptProcessorNode` browser capture, **no hand-rolled VAD** (provider owns turn boundaries), keyless replay backend for CI. v0.6.11.
**Method:** primary vendor developer docs and source repositories read directly (no marketing pages, no listicles), gathered with parallel subagent extraction and verified against my own page reads. Every non-obvious claim carries the URL it came from. Anything not confirmable from primary docs is marked **UNVERIFIED** and listed in §6.
**Confidence:** High on transports, turn detection, barge-in mechanics, tool surfacing, and session/handoff for all eight platforms — these are documented behaviours with named events/fields. Medium on observability *coverage* and on mid-session rejoin, where several vendors explicitly document nothing (absence of a doc is itself the finding). The OpenAI surface is moving fast (`gpt-realtime-2.1`, `gpt-live-1`); treat exact event names as current-at-date.
**Platforms examined:** ElevenLabs Agents (Conversational AI), Vapi, Retell AI, LiveKit Agents, Pipecat, OpenAI Realtime API + GPT-Live, Google Gemini Live API, plus open-source building blocks (Silero VAD, LiveKit turn detector, Pipecat Smart Turn, vocode).

---

## 0. Bottom line

1. **Our no-hand-rolled-VAD position is not just defensible in 2026 — it is the direction the leaders moved.** OpenAI's GPT-Live *removed the turn detector from the audio path entirely* and made the voice model full-duplex ([openai.com](https://openai.com/index/continuous-voice-interaction-with-gpt-live/)). Every managed platform (ElevenLabs, Vapi, Retell, LiveKit-with-realtime-model, Gemini) owns turn boundaries server-side. Turn-end detection is a solved, provider-owned concern; clients that reimplement it inherit resampling, a VAD gate, and a turn-buffer policy.
2. **The genuinely reusable, licence-clean open-source turn detectors exist (Smart Turn BSD-2, Silero MIT, `fd-vad` MIT) but every one of them drags us back toward the hand-rolled design** (24→16 kHz resample + VAD gate + buffering). LiveKit's turn detector is the strongest model on the only public benchmark yet is **licence-locked to LiveKit Agents** and therefore off-limits. See §5.
3. **What is *not* solved by anyone, and is our real engineering surface, is the non-audio half:** reconnect/resume semantics, barge-in state rollback (especially *not* cancelling dispatched tools), a spoken-progress channel for long tool work, and per-turn latency telemetry. These are where the platforms converge on the *same* answer, and where a plugin earns its keep.
4. **Table stakes are turn/barge-in correctness, per-turn latency telemetry, a durable session identity with an explicit resume contract, first-class non-blocking tool events with a spoken-progress channel, and observable turn-end signals** (§4).

## 1. Platform findings (condensed)

### ElevenLabs Agents (Conversational AI)
Fully managed pipeline: proprietary ASR + versioned turn model (`turn_v3` default) + your LLM + ElevenLabs TTS. Three transports documented (WebSocket, WebRTC via LiveKit, SIP); the JS SDK defaults **voice→WebRTC, text→WebSocket** ([libraries/java-script](https://elevenlabs.io/docs/eleven-agents/libraries/java-script)). On the WebSocket path the docs put media resilience explicitly on the client: "Implement a jitter buffer", "handle audio queuing", "Implement reconnection logic", ping/pong RTT monitoring ([libraries/web-sockets](https://elevenlabs.io/docs/eleven-agents/libraries/web-sockets)). Turn model is proprietary and **not provider-agnostic** (only `turn_v2`/`turn_v3` selection); raw signals are exposed opt-in via `client_events` (`vad_score`, `interruption`, `internal_turn_probability`) ([api-reference/agents/create](https://elevenlabs.io/docs/eleven-agents/api-reference/agents/create)). Barge-in truncates spoken output and the client must rewrite UI state from `agent_response_correction`; `interruption_mode: disable_during_tool` can suppress interrupts mid-tool. Long work uses ambient **tool-call sounds** and **soft-timeout filler speech**, not verbal progress. Durable `conversation_id` exists; **context does not survive reconnects** as a feature — documented pattern is statelessness between conversations plus re-injection via dynamic variables ([workflows/post-call-webhooks](https://elevenlabs.io/docs/eleven-agents/workflows/post-call-webhooks)). Observability is the strongest of the managed set: **OpenTelemetry traces** in OTLP JSON, one `traceId` per conversation, plus per-turn `conversation_turn_metrics` ([customization/opentelemetry-traces](https://elevenlabs.io/docs/eleven-agents/customization/opentelemetry-traces)). Capture-side **AEC is undocumented** — the only claim is a marketing blog.

### Vapi
Four transports (SIP, telephony, WebSocket, WebRTC) and — uniquely among the managed pair — a documented **raw PCM WebSocket transport** (`transport.provider: 'vapi.websocket'`, `wss://api.vapi.ai/<callId>/transport`, `pcm_s16le`, auto-resampling, docs cite 16 kHz default) ([calls/websocket-transport](https://docs.vapi.ai/calls/websocket-transport)). Turn-taking is deliberately **non-replaceable**: orchestration "runs exclusively on Vapi infrastructure" even with BYO STT/LLM/TTS ([security-and-privacy/data-flow](https://docs.vapi.ai/security-and-privacy/data-flow)). The closest we get to owning endpointing is `smartEndpointingPlan.provider: custom-endpointing-model`, where *their* infra POSTs each decision to *our* server and we return a `timeoutSeconds` — i.e. a policy callback, **not** a client VAD ([customization/speech-configuration](https://docs.vapi.ai/customization/speech-configuration)). Barge-in is VAD-utterance-start gated by `interruptionPhrases`/`acknowledgementPhrases`/`stopSpeakingPlan.numWords`, and `user-interrupted` carries the **same `turnId` as `model-output`** precisely so the client discards that turn's tokens. Tools are server-side by default (`tool-calls` server message) with a stated hard limit: **"Client-side tools cannot send a result back to the model"** ([tools/client-side-websdk](https://docs.vapi.ai/tools/client-side-websdk)). Verbal progress exists via `request-start` messages and `bot_say`; `async: true` tools supported. Durable `call.id`; squads/handoffs with `contextEngineeringPlan`. Observability via server-URL events (`model-output.turnId`, `user-interrupted.turnId`, `speech-update.turn`) — no per-turn latency webhook documented.

### Retell AI
Phone/browser/LLM-WebSocket transports; the **audio WebSocket is explicitly deprecated** ("use Custom Telephony or Web Call SDKs"), so the way to plug in a custom brain is the **text-only LLM WebSocket**, where Retell owns audio/VAD/turn-taking and asks you for text on `response_required` ([integrate-llm/overview](https://docs.retellai.com/integrate-llm/overview), [api-references/audio-websocket](https://docs.retellai.com/api-references/audio-websocket)). Turn detection is ASR-pipeline endpointing plus "holds off longer when it detects the caller has not finished their thought"; knobs are `stt_mode`, `custom_stt_config.endpointing_ms`, `responsiveness` (documented delay formula up to 5.5 s) ([build/transcription-mode](https://docs.retellai.com/build/transcription-mode)). Barge-in is `interruption_sensitivity` (0–1). **Rollback semantics are the clearest of any platform and the most important lesson:** buffered agent audio is cleared (`clear` event) and stale responses are discarded via a **monotonic `response_id`**, but **in-flight tool calls are NOT cancelled** — "The request to your endpoint is not cancelled... it runs to completion... make side-effecting actions... idempotent" ([integrate-llm/integrate-function-calling](https://docs.retellai.com/integrate-llm/integrate-function-calling)). Spoken progress: "Talk While Waiting" / "Talk After Action Completed" and `speak_during_execution`. **Best latency telemetry of the set:** `e2e`, `llm`, `tts`, `llm_websocket_network_rtt`, each with **p50/p90/p95/p99** ([reliability/check-actual-latency](https://docs.retellai.com/reliability/check-actual-latency)). Reconnect is documented with concrete policy: ping/pong every 2 s, close after 5 s, up to 2 reconnect attempts on keepalive loss / 4 on abnormal close ([integrate-llm/setup-websocket-server](https://docs.retellai.com/integrate-llm/setup-websocket-server)).

### LiveKit Agents
WebRTC-first (participant/room/track model; ICE/UDP → TURN/UDP → ICE/TCP → TURN/TLS fallback) with **automatic signalling reconnect + ICE restart** and explicit `Reconnecting`/`Reconnected` events, plus SIP telephony ([intro/basics/connect](https://docs.livekit.io/intro/basics/connect/), [agents/v1/start/telephony](https://docs.livekit.io/agents/v1/start/telephony)). Turn detection is the richest documented taxonomy: modes are **turn-detector model (default), `realtime_llm`, `vad`, `stt`, `manual`** — and it is honestly explicit that with a server-side-turn-detection realtime model, `InterruptionOptions` is largely ignored and "Tune interruption on the model itself instead" ([agents/logic/turns](https://docs.livekit.io/agents/logic/turns/)). The audio `TurnDetector` v1 is the top model on `livekit/eot-bench`, v1-mini runs locally on CPU — **both under the LiveKit Model License**, framework-locked (§5) ([agents/logic/turns/turn-detector](https://docs.livekit.io/agents/logic/turns/turn-detector/)). Barge-in: pauses speech and "automatically truncates its conversation history to include only the portion of the speech that the user heard"; adaptive (barge-in) model distinguishes backchannels; false-interruption recovery via `false_interruption_timeout` + `resume_false_interruption` ([adaptive-interruption-handling](https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling/)). Realtime-model interruption gating note: "Models that keep turn-taking on their own signals, such as the Gemini Live API, aren't compatible with the client-side gate." Observability is the reference implementation: per-turn `ChatMessage.metrics` (`e2e_latency`, `llm_node_ttft`, `tts_node_ttfb`), per-plugin metrics, session usage, and **`InterruptionMetrics`** (`num_interruptions`, `num_backchannels`, `detection_delay`) — with the key note that **realtime models populate `ttft` but not `llm_node_ttft`/`tts_node_ttfb`** ([testing/observability/data](https://docs.livekit.io/testing/observability/data/)).

### Pipecat
Open-source pipeline (frame processors in two lanes: high-priority **SystemFrames** vs queued **DataFrames/ControlFrames**). Transport guidance is opinionated and useful: "For any client-to-server voice application, WebRTC is the right choice. WebSocket... is built on TCP, which makes it a poor fit for real-time audio"; WS is for telephony media streams and server-to-server ([client/concepts/choosing-a-transport](https://docs.pipecat.ai/client/concepts/choosing-a-transport), [learn/transports](https://docs.pipecat.ai/pipecat/learn/transports)). Turn detection: **Silero VAD** for start plus **Smart Turn (default, `LocalSmartTurnAnalyzerV3`)** for end; VAD and turn detection are separate concerns, with `UserTurnInferenceCompletedFrame` for external completeness signals ([learn/speech-input](https://docs.pipecat.ai/pipecat/learn/speech-input)). Barge-in is the cleanest **rollback spec of all**: an `InterruptionFrame` is a SystemFrame handled immediately; every processor cancels its task and discards queued Data/Control frames, in-flight LLM completions are cancelled, TTS clears buffers, the output transport **drains unplayed audio**, and the assistant context commits **only the spoken-so-far text** ("the bot's message ends where the user cut it off, not where the LLM's generation ended") ([fundamentals/interruptions](https://docs.pipecat.ai/pipecat/fundamentals/interruptions)). Realtime services (Gemini Live, OpenAI Realtime) "handle interruption detection on the provider side" and Pipecat just flushes local output. Backchannel filtering is a model (Krisp VIVA IP) or a mute strategy.

### OpenAI Realtime API
Two transports with clear guidance: **WebRTC for browsers/mobile, WebSocket for server-to-server**; both carry the same event surface ([guides/realtime-websocket](https://developers.openai.com/api/docs/guides/realtime-websocket)). Sessions are stateful, **max 60 minutes** ([guides/realtime-conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)). Turn detection is provider-native and configurable: `server_vad` (`threshold`, `prefix_padding_ms`, `silence_duration_ms`) or `semantic_vad` (`eagerness` low/medium/high/auto) ([guides/realtime-vad](https://developers.openai.com/api/docs/guides/realtime-vad)). Barge-in on WS is a documented **client procedure**: stop playback, note how much played, then send `conversation.item.truncate` with `audio_end_ms`; on WebRTC/SIP the server truncates unplayed audio automatically. Tools: client `function` tools vs **server-executed `mcp` tools** with approval lifecycle, and a **sideband WebSocket** (`wss://api.openai.com/v1/realtime?call_id=...`) so tools/business logic stay server-side ([guides/realtime-mcp](https://developers.openai.com/api/docs/guides/realtime-mcp), [guides/realtime-server-controls](https://developers.openai.com/api/docs/guides/realtime-server-controls)). Observability: usage on `response.done`; no built-in OTel (contrast ElevenLabs).

### OpenAI GPT-Live (`gpt-live-1`)
The most important reference for our architecture. It is **full-duplex and has no turn detector in the audio path**; the voice model manages listening/speaking and **delegates** reasoning + tools to a backend ([guides/live-delegation](https://developers.openai.com/api/docs/guides/live-delegation)). Design points to copy: media on a **dedicated fast path**, delegation on an **async RPC boundary** ("a slow tool call... cannot stall the flow of media"); **context append channels** — `session.commentary.append` for results it should say aloud, `session.thinking.append` for quiet facts, `session.instructions.append` to steer (500-token limit, `delegation_id: null` for session-wide); and an explicit warning that **interrupting speech does not cancel backend work** ("Interrupting the spoken conversation leaves backend work running"; "Keep operation status in your application so restarting does not repeat completed actions"). Long conversations: server-side compaction with a **live instance handoff** at 90% context ("starts a replacement voice engine within the same session"; up to 8,192 tokens of history carried), and a **fork** primitive to resume a saved conversation in a **new session ID** ([guides/live-conversations](https://developers.openai.com/api/docs/guides/live-conversations)). Prompting guide formalises spoken **preambles** ("I'll check that order now") as first-class behaviour ([guides/voice-prompting](https://developers.openai.com/api/docs/guides/voice-prompting)).

### Google Gemini Live API
WebSocket-only first-party (`BidiGenerateContent`); **WebRTC only via partners** (Daily, LiveKit, Twilio, Voximplant); Google's own sample says **"Use headphones"** because there is no provider AEC ([ai.google.dev/api/live](https://ai.google.dev/api/live), [gemini-skills](https://github.com/google-gemini/gemini-skills/blob/main/skills/gemini-live-api-dev/SKILL.md)). Turn detection is provider-native and highly tunable (`startOfSpeechSensitivity`, `endOfSpeechSensitivity`, `prefixPaddingMs`, `silenceDurationMs` 500–800 ms recommended) with three modes: auto VAD, hybrid (client sends `audioStreamEnd` to finalise early), manual (`automaticActivityDetection.disabled` + `activityStart`/`activityEnd`) ([gemini-api/docs/live-api/capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities)). Barge-in: server sends `serverContent.interrupted: true` and the client **must** flush its playback queue; the server also emits **`toolCallCancellation.ids[]`** — the only provider that explicitly tells you to undo tool side-effects — while "Only the information already sent to the client is retained in the session history". But the documented limitation that matters to us: LiveKit states Gemini Live **"doesn't support client-side turn-taking"** and "aren't compatible with the client-side gate". Reconnect is first-class: `sessionResumption` handles (2 h Gemini / 24 h Vertex, ~10 min post-drop window), `goAway` ~60 s before the ~10-min connection cap, and context-window compression for long sessions. Async tools: `behavior: NON_BLOCKING` with `scheduling` INTERRUPT/WHEN_IDLE/SILENT; the extended-thinking model "streams intermediate conversational fillers while processing" and `interaction_status: IN_PROGRESS|IDLE` tells you when it is truly done ([gemini-api/docs/live-api/thinking](https://ai.google.dev/gemini-api/docs/live-api/thinking), [asynchronous-function-calling](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/asynchronous-function-calling)). Observability: `usageMetadata`, transcription events, `voice_activity`, `turnCompleteReason`; **no per-stage latency tracing** documented.

**One-line read:** correctness of the audio loop is commoditised; the differentiators are (i) how honestly a platform documents *what does not roll back*, (ii) whether it hands you a session identity you can resume, and (iii) whether it gives you a latency-broken-down telemetry surface. Retell and LiveKit win on (i)/(iii); ElevenLabs wins on (iii) via OTLP; Gemini wins on (ii); GPT-Live is the architectural template for (i).

## 3. (b) Recommendations by dimension

> Every recommendation below must hold three constraints: **no hand-rolled VAD/endpointing** (forbidden design), **self-containment** (no runtime dependency on a third-party plugin), **keyless CI** (conformance runs on recorded frames with no credential). Where a recommendation would violate one, it says so explicitly.

### 3.1 Transport & reconnect

**What we should do.**
- Keep **WebSocket as the server↔provider seam** (matches GPT-Live's primary WS, our existing transport, and Retell/Vapi's text/audio WS). Do **not** chase WebRTC: our transport is chosen, and Pipecat's own guidance confines WS to server-to-server/telephony — which is exactly our server↔provider leg, not the browser↔server leg we already delegate to `ScriptProcessorNode`.
- Treat **reconnect as an app-driven replay contract with a durable session id**, never as a provider feature. Concretely: on socket drop, re-establish, re-issue the session start/attach, and replay a **bounded** conversation context we hold. Retell is the model (`auto_reconnect` + ping/pong every 2 s, close after 5 s, capped attempts + documented close codes); GPT-Live is the model for *what to replay* (start a new session seeded with saved history, "check the status of outstanding backend work before repeating it").
- Add explicit **capture-side audio constraints** (`echoCancellation`, `noiseSuppression`, `autoGainControl` in `getUserMedia`) and document "headphones recommended". No platform documents provider-side AEC — ElevenLabs' AEC claim is a blog, Google's own sample literally says "use headphones". If we assume AEC happens for free, the agent will self-interrupt on speaker output.
- Own a **jitter/playback queue** for the WS audio path. ElevenLabs names jitter buffer + playback queueing + ping-based RTT as the client's job; assume the same for us.

**Lazy failure mode:** assuming WS/TCP gives us ordering *and* smooth real-time audio, and skipping the jitter buffer / playback queue / retry logic. Pipecat and ElevenLabs both say a WS audio path needs all three; without them you get stutter and overlapping audio on any real network.
**Expensive failure mode:** building a WebRTC stack (or taking a runtime dep on a media/plugin library) to "do it properly". That is the self-containment violation and a large maintenance surface for a plugin that already owns its transport.

**Evidence trail:** connect/reconnect — [Retell setup-websocket-server](https://docs.retellai.com/integrate-llm/setup-websocket-server); jitter/queue/retry — [ElevenLabs web-sockets](https://elevenlabs.io/docs/eleven-agents/libraries/web-sockets); WS-vs-WebRTC trade-off — [Pipecat choosing-a-transport](https://docs.pipecat.ai/client/concepts/choosing-a-transport); AEC absence — [Gemini Live skill](https://github.com/google-gemini/gemini-skills/blob/main/skills/gemini-live-api-dev/SKILL.md), [ElevenLabs blog (flagged as non-doc)](https://elevenlabs.io/blog/conversational-ai-webrtc); GPT-Live reconnect semantics — [guides/live-conversations](https://developers.openai.com/api/docs/guides/live-conversations).

### 3.2 Turn detection / endpointing

**What we should do.**
- **Stay provider-owned; do not ship a detector.** The single strongest piece of evidence is architectural, not competitive: GPT-Live removed the turn detector from the audio path because full-duplex listening makes it unnecessary. LiveKit's own docs concede that with a realtime model you "Tune interruption on the model itself". Provider-native is a legitimate 2026 position, not a shortcut.
- **Surface, don't compute.** Expose the provider's turn/VAD signals on our seam wire so the harness/UI agree on turn state: OpenAI `input_audio_buffer.speech_started/stopped`; Gemini `interrupted`, `voice_activity`, `interaction_status`, `turnCompleteReason`; ElevenLabs `vad_score` / `internal_turn_probability`; Vapi `speech-update`; Retell `turntaking`. This satisfies "a file nothing reads is not a contract" — the signal rides the wire our replay backend already consumes.
- **Expose endpointing knobs as config with defaults, not code.** OpenAI `server_vad` (`threshold`, `prefix_padding_ms`, `silence_duration_ms`) and `semantic_vad.eagerness`; Gemini's sensitivities/`silenceDurationMs`. These are exactly the tunables a caller wants, and they cost us nothing to pass through.
- If we ever need an in-process acoustic signal (e.g. local barge-in on the browser leg), **Silero VAD (MIT)** is the only clean, tiny, offline option — but note the convergence trap below.

**Lazy failure mode:** adopting LiveKit's turn detector because it tops the benchmark. It is **licence-locked** ("ONLY together with the LiveKit Agents framework... cannot use them on a standalone basis or with any other frameworks") and partly cloud-served — unusable in a self-contained plugin.
**Expensive failure mode:** adopting Smart Turn (BSD-2) or Silero "properly". Both take **16 kHz mono**; Silero additionally needs exact 512-sample chunks, and 24 kHz is not an integer multiple of 16 kHz. Adopting either means adding (i) 24→16 kHz resampling, (ii) a VAD gate, and (iii) our own turn-buffering policy — i.e. **re-creating the exact hand-rolled layer the design forbids.** Silero as a vendored, single-purpose barge-in gate is defensible; Smart Turn as a "semantic EOT layer" is the forbidden design wearing an OSS badge.

**Evidence trail:** GPT-Live no detector — [openai.com](https://openai.com/index/continuous-voice-interaction-with-gpt-live/); LiveKit realtime caveat — [agents/logic/turns](https://docs.livekit.io/agents/logic/turns/); OpenAI knobs — [realtime-vad](https://developers.openai.com/api/docs/guides/realtime-vad); Gemini knobs — [live-api/capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities); OSS licences/inputs — see §5.

### 3.3 Barge-in & state rollback

**What we should do.** Implement **one** `interrupt` path at the seam with four ordered obligations, distilled from the platforms that document them:
1. **Silence the agent immediately** — stop playback and **drain the local audio queue**. (Pipecat: "the output transport drains its audio queue, discarding audio that was generated but not yet played"; Gemini: "You must immediately discard your client-side audio buffer".)
2. **Truncate the conversation to what was actually heard** so the next turn's model context ends where the user cut in. OpenAI gives the primitive: `conversation.item.truncate {item_id, audio_end_ms}`; Pipecat commits only the spoken-so-far text. If the provider truncates for us (OpenAI WebRTC/SIP), don't double-do it — detect and skip.
3. **Supersede in-flight work without pretending to cancel it.** Tag every queued response and tool request with a **monotonic turn/response id** (Vapi `turnId`, Retell `response_id` + auto-increment, GPT-Live "task revision + operation ID"). On interrupt, mark prior ids superseded and **discard late results**; do not rely on the provider cancelling a dispatched tool.
4. **Make tool side-effects idempotent** keyed on `sessionId + toolArgs`. Retell states the truth plainly: an interrupted-then-retried turn "routinely runs a side-effecting tool twice"; Gemini is the only provider that even attempts coordinated cancellation, via `toolCallCancellation.ids[]` with a "clients may attempt to undo" caveat. Design for *no* cancellation.

**Lazy failure mode:** clearing only local audio and leaving the transcript intact. The next model turn then "remembers" words the user never heard, producing bizarre continuations ("as I was saying...") — this is the most common barge-in bug in the wild.
**Expensive failure mode:** trying to *cancel* a dispatched tool by aborting the HTTP request, or attempting to compensate side effects. Retell documents the request runs to completion up to its timeout; a naive abort leaves you unsure whether the write happened. Idempotency + discard-late-results is the correct, cheaper invariant.

**Evidence trail:** [Pipecat interruptions](https://docs.pipecat.ai/pipecat/fundamentals/interruptions); [Retell integrate-function-calling](https://docs.retellai.com/integrate-llm/integrate-function-calling); [OpenAI realtime-conversations](https://developers.openai.com/api/docs/guides/realtime-conversations); [Gemini capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities) + [api/live](https://ai.google.dev/api/live); [GPT-Live delegation](https://developers.openai.com/api/docs/guides/live-delegation); [Vapi speech-configuration](https://docs.vapi.ai/customization/speech-configuration).

### 3.4 Tool-call surfacing & long-running work

**What we should do.** Our plugin already has the right shape — the voice **delegates** an unanswerable question to a DSH session and speaks the answer back. Adopt the GPT-Live contract for that delegation:
- **Don't block the media loop.** Keep the spoken conversation on the fast path and delegated DSH work on an async boundary (GPT-Live: "a slow tool call... cannot stall the flow of media"; Gemini: `NON_BLOCKING` + `scheduling`).
- **Two progress channels, not one.** Mirror `commentary` vs `thinking`: a *speakable* channel for short, natural preambles ("I'll check that now") and a *quiet* channel for facts that inform later replies without being voiced. This is how you handle long work without narrating internals.
- **Speak short preambles, not status logs.** Follow OpenAI's prompting guide: one short sentence, describe the action not the reasoning, vary wording, never say "let me think" or reveal chain-of-thought.
- **Return tool errors as results the model can phrase**, with a structured error flag (`is_error` / `successful: false` / an error payload), rather than having the transport invent an apology. And always emit a terminal event for every tool call — Retell's lesson is that a missing terminal (`content_complete: true` in a `finally`) leaves the agent silent with **no error raised anywhere**.

**Lazy failure mode:** silently `await` a multi-second DSH turn. The caller hears dead air and assumes the agent died — the single biggest perceived-quality killer in voice agents, and the reason every managed platform ships filler/progress speech.
**Expensive failure mode:** speaking a step-by-step narration of internal tool activity, or leaking backend reasoning. OpenAI warns explicitly that preambles are **not** chain-of-thought; over-narrating both raises latency and exposes internals.

**Evidence trail:** [GPT-Live delegation and tools](https://developers.openai.com/api/docs/guides/live-delegation); [Prompting Realtime models (preambles)](https://developers.openai.com/api/docs/guides/voice-prompting); [Gemini async function calling](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/asynchronous-function-calling); [Retell integrate-function-calling](https://docs.retellai.com/integrate-llm/integrate-function-calling); [Vapi tools](https://docs.vapi.ai/tools); [ElevenLabs tool-call-sounds](https://elevenlabs.io/docs/eleven-agents/customization/tools/tool-configuration/tool-call-sounds).

### 3.5 Session state & handoff

**What we should do.** Make the voice session a **transient front-end onto a durable DSH session**, and make the durable id the contract:
- Define one **durable session id** at the seam (analogous to ElevenLabs `conversation_id`, Vapi/Retell `call_id`, Gemini `session_id` + resumption handle, GPT-Live session id). Persist it with the recorded frames so replay/CI can key on it.
- **Hold task state in the harness, never only in the voice session.** GPT-Live is explicit ("Keep operation status in your application so restarting does not repeat completed actions"); ElevenLabs' documented model is statelessness between conversations plus re-injection via dynamic variables.
- **Reconnect = fork/reseed, not resume.** Provider context does not survive a socket drop on OpenAI Realtime (60-min cap, no documented mid-session resume) and only survives on Gemini with resumption explicitly enabled. So the handoff must be app-driven replay of a bounded history into a fresh session — exactly GPT-Live's fork pattern.
- **Voice↔text handoff is the delegation boundary we already have.** Because the voice delegates to a DSH session, that same session should be resumable from a text client by id; this is the natural, cheap handoff and needs no new provider primitive.

**Lazy failure mode:** assuming the provider keeps the conversation across a reconnect. It doesn't — uniformly. The first dropped socket silently loses context and the user must repeat themselves.
**Expensive failure mode:** building a bespoke provider-side session store that shadows/duplicates DSH session state, creating two sources of truth for "what has this agent done". Also: don't invent a *metadata file* to carry this — see the note on "a file nothing reads is not a contract" below.

> **Applying "a file nothing reads is not a contract":** do **not** ship a standalone `voice-session.json` (or similar) that no consumer parses. Session identity, turn ids, and task revisions must ride the event wire that the replay backend and conformance suite already consume. If nothing reads it, it isn't a session contract; it's decoration.

**Evidence trail:** [GPT-Live managing sessions](https://developers.openai.com/api/docs/guides/live-conversations); [OpenAI realtime-conversations (60-min cap)](https://developers.openai.com/api/docs/guides/realtime-conversations); [Gemini session management](https://ai.google.dev/gemini-api/docs/live-api/session-management); [ADK live sessions (transfer drops the handle)](https://adk.dev/live/sessions/); [ElevenLabs post-call webhooks](https://elevenlabs.io/docs/eleven-agents/workflows/post-call-webhooks); [Retell get-call/update-live-call](https://docs.retellai.com/api-references/get-call).

### 3.6 Observability

**What we should do.** Adopt the convergent essential set — and critically, **make our replay backend emit these same events so keyless conformance asserts on the telemetry contract, not just the frames** (otherwise, per the maintainer's rule, the telemetry is a file nothing reads):
- **Per-turn latency breakdown.** The event the whole industry measures is *user stopped speaking → first agent audio* (LiveKit `e2e_latency`; Retell `e2e`, both excluding tool-only turns and frontend network). Decompose it the LiveKit/Vapi way: **EOU/end-of-utterance delay + provider TTFT + TTS TTFB**. Note the honest detail that LiveKit documents: with a **realtime model, only `ttft` is populated** and the STT/LLM node fields are empty — which is our case, so we should not build dashboards that assume components we don't have.
- **Transcript events** — user vs agent, interim vs final, with timestamps where the provider gives them (GPT-Live `start_ms`/`end_ms`; Gemini `inputTranscription`/`outputTranscription` "close to the corresponding audio").
- **Turn + interruption events** — turn start/stop, an interruption with a **reason and turn id**, and false-interruption/backchannel counters. LiveKit's `InterruptionMetrics` (`num_interruptions`, `num_backchannels`, `detection_delay`, `prediction_duration`) is the reference shape.
- **Usage/cost** — tokens split by **modality** (audio vs text vs cached; OpenAI/LiveKit), plus **session seconds** (GPT-Live `usage.seconds`; Gemini `usageMetadata`). This matters because Gemini bills the whole context window per turn and counts audio at ~25 tokens/sec.

**Lazy failure mode:** logging unstructured free-text lines (`console.log("interrupted")`) that no consumer parses or asserts on. That is telemetry theatre — invisible in CI and unqueryable in production.
**Expensive failure mode:** standing up a full OTel collector / LangSmith-style tracing pipeline inside a plugin. ElevenLabs and LiveKit publish OTLP *shapes*; we should **emit** the same field names in our own event stream (cheap, testable) and let a downstream consumer decide whether to ship them to a collector — rather than take a runtime dependency on a telemetry stack.

**Evidence trail:** [LiveKit observability data](https://docs.livekit.io/testing/observability/data/) and [metrics API](https://docs.livekit.io/reference/python/livekit/agents/metrics/index.html); [Retell check-actual-latency](https://docs.retellai.com/reliability/check-actual-latency); [ElevenLabs OTLP traces](https://elevenlabs.io/docs/eleven-agents/customization/opentelemetry-traces) and [per-turn metrics](https://elevenlabs.io/docs/eleven-agents/api-reference/conversations/get); [Vapi server-URL events](https://docs.vapi.ai/server-url/events); [GPT-Live usage/close](https://developers.openai.com/api/docs/guides/live-conversations).

## 4. (c) Table stakes for a voice agent in 2026

Absent any of these, the agent is conspicuously behind — not "missing a feature" but "clearly built by someone who hasn't shipped voice".

1. **Barge-in that actually stops the audio and truncates the unheard tail.** Every platform stops playback and drains the queue on user speech, and keeps the conversation history consistent with what the user heard (OpenAI `conversation.item.truncate`; Pipecat spoken-so-far commit; LiveKit "truncates its conversation history to include only the portion of the speech that the user heard"). A voice agent that talks over the user, or that "remembers" words it never spoke, signals immediately that it is unfinished.
2. **A per-turn latency breakdown that is observable, not inferred.** E2E (end-of-user-speech → first agent audio), decomposed into end-of-utterance + first-token/first-byte, plus interruption counters. LiveKit, Retell, Vapi, and ElevenLabs all expose this; a voice product with no latency telemetry cannot be tuned and will regress silently.
3. **A durable session identity with an explicit resume contract** — even when resumption is app-driven replay. `conversation_id` / `call_id` / `session_id` + resumption handle / forged session id are universal; relying on the socket staying up is the classic amateur assumption.
4. **Tool calls as first-class, non-blocking events with a spoken-progress channel and idempotency keyed to the turn/session.** Because no platform reliably cancels a dispatched tool, and all of them let a slow tool stall the user unless work is pushed off the media path (GPT-Live async delegation; Gemini `NON_BLOCKING`; Retell idempotency mandate).
5. **Turn-end *visibility* without turn-end *ownership*:** the client can observe turn start/stop (and, where offered, a confidence/prediction signal — GPT-Live transcripts, Gemini `voice_activity`, ElevenLabs `vad_score`, Vapi `speech-update`) so the UI and the harness agree on whose turn it is, while the provider remains the authority on the boundary.

| Project | What it is | Licence | Runs offline? | Input | Vendor-locked? | Verdict for us |
|---|---|---|---|---|---|---|
| **Silero VAD** | audio VAD (speech/non-speech) | **MIT** | yes, ~2 MB ONNX/JIT, CPU | 8/16 kHz, **512-sample chunks @16k** | no | only safe acoustic gate; still needs 24→16 kHz resample |
| **LiveKit Turn Detector** (text + audio) | Qwen2.5-0.5B EOU / audio EOU | **LiveKit Model License — NOT OSI** | text: weights local but use-restricted; v1: cloud-only; v1-mini: bundled native lib | text: STT transcript; audio: 16 kHz + VAD ≥250 ms | **YES — LiveKit Agents only** | **off-limits** |
| **Pipecat Smart Turn v3.x** | Whisper-Tiny encoder + linear head, ~8M | **BSD-2-Clause** | yes, 8 MB ONNX, ~12 ms CPU | 16 kHz mono float32, VAD-gated | no | strongest licence-clean option, **but adopting it recreates the hand-rolled layer** |
| **livekit/eot-bench + data** | EOT benchmark + 14-lang dataset | **Apache-2.0** | yes | audio + transcripts | no | **adopt for evaluating any policy we ship** |
| **vocode-core** | full voice-agent framework | MIT | yes | STT output + silence/punctuation | no (endpointing is STT-dependent) | reference only; **unmaintained since 2024-11** |
| **fd-vad** | WavLM + Qwen2.5 LoRA, streaming audio EOU | MIT | yes, ~1.5 GB bundle | 16 kHz streaming audio | no | closest to our assumption, but research-grade |
| Namo / anyreach / doodod / TurnSense | small text EOU classifiers | Apache-2.0 (some with extra restrictions) | yes | transcript | no | only usable if a transcript already exists |

**Notes.** Silero's README badge is mislabelled (CC BY-NC image pointing at the MIT LICENSE) — the repo and GitHub metadata say MIT. LiveKit's *plugin package* is Apache-2.0, but the *model* is under the LiveKit Model License, which forbids standalone/framework-other use — a genuine trap for anyone who reads the plugin licence and stops there. The `eot-bench` leaderboard (v1 9.9% false cut-offs @300 ms vs silence-only VAD baseline 55.6%, Smart Turn v3.2 35.2%) is the only public, reusable way to judge any endpointing policy — and it is Apache-2.0.

**Consequence for `dsh-openai-live`:** the correct move is **not to adopt any of these detectors**. We are not merely deferring to the provider — we are choosing not to re-acquire the resampling + VAD-gate + buffering complexity that every audio-native OSS option requires and that the design explicitly forbids. If we ever need an *acoustic* barge-in hint, vendor **Silero (MIT)** as a single-purpose gate, and adopt **`eot-bench`** to prove we didn't make turn-taking worse.

## 6. UNVERIFIED / open questions

Grouped; each is "docs are silent" unless stated otherwise.

- **AEC / noise suppression / jitter buffers** are undocumented for **every** platform's provider side. ElevenLabs' AEC claim is a marketing blog, not docs; Retell puts it on "the user's side"; Google's own sample says "use headphones". We are on our own here.
- **Mid-session rejoin:** no resume protocol for ElevenLabs; undocumented for Vapi `vapi.websocket`; Retell only exposes monitor + one-way Take Over for web calls; OpenAI Realtime has a 60-min cap and no documented mid-session resume; Gemini is the only one with a real resumption handle (and it is dropped on ADK agent transfer).
- **Whether barge-in cancels in-flight LLM/tool work:** only Retell states the answer explicitly (tools are **not** cancelled); Gemini emits `toolCallCancellation`; for ElevenLabs/Vapi the cancellation semantics are not documented. Treat as "assume not cancelled" everywhere.
- **Spoken tool-error policy:** undocumented for Gemini ("return a FunctionResponse" pattern only) and for ElevenLabs (only `is_error`/`status` flags); Vapi links error-handling guides whose exact content reviewers could not retrieve.
- **Vapi 24 kHz:** docs cite a 16 kHz PCM default plus 8 kHz and 44.1 kHz resampling examples; **24000 is not listed** — whether `vapi.websocket` accepts 24 kHz is unconfirmed.
- **Pipecat WebRTC-deprecation details:** the deprecated Gemini-Live / OpenAI-WebRTC *client* transports are noted in docs, but not every server-side transport pairing is affirmatively documented as current.
- **Gemini client-side turn-taking:** LiveKit says Gemini "doesn't support client-side turn-taking", while Google's own manual-VAD docs and LiveKit's Gemini plugin show disabling auto-VAD — the two are not reconciled by either party (unresolved).
- **Benchmark provenance:** the `eot-bench` leaderboard numbers are produced by LiveKit.
- **Observability field completeness:** Vapi documents no per-turn latency webhook; Gemini documents no per-stage latency tracing; ElevenLabs' exact `conversation_turn_metrics` key set and dashboard "agent response latency" definition are not fully specified.
